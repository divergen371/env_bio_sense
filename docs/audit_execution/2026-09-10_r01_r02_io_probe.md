## 前回記録の訂正

「一覧更新単独でも再起動したので `/api/files` に発火routeを確定」は断定が強すぎた。
通常の `boot()` は状態API 5本と一覧を並行要求し、その後も状態を10秒周期で取得する。
一覧更新ボタンを押しても、状態取得が停止するわけではない。
既存ログは `async_tcp` のWatchdog再起動を示すが、停止中のcallbackと段階までは示していない。
`/api/files` は有力候補として残し、状態のみ／一覧のみの比較で確定する。

## R02 静的調査: 現在の実行経路

| 実行元 | core / 基本優先度 | Storage mutex内の処理・待機点 |
|---|---|---|
| loopTask | Arduino設定 / 1 | 5秒周期の `appendRecord`（format・FRAM WAL append/read-back/checkpoint）、センサー経由のevent・校正・保存状態取得、週次Archive候補走査 |
| StorageTask | 1 / 1 | 5秒周期の `flushPendingToSd`。pending全件を1回の排他内で処理。20 ms周期のPPG updateも同じtask |
| async_tcp | core固定なし / 10 | `/api/files`の同期再帰走査、状態getter、event取得、現行CSV download前のforceFlush、downloadのopen/seek/read/close、削除 |
| ArchiveTask | 0 / 1 | 入力検査・ZIP read/write・CRC検証・rename・検証後削除。I/OごとにStorage mutex。別途statusMutexも無期限待ち |
| WeatherTask | 0 / 1 | AMeDAS provenance CSVの追記と再open照合、気圧状態反映に伴うevent |
| DisplayTask | 1 / 1 | Storage mutexの直接利用なし。SensorManager snapshotを描画し、OLED送信で共通I²C mutexを使用 |

`src/main.cpp`、`src/storage/storage_manager.cpp`、`src/services/{web_server_service,archive_manager,ppg_session_manager}.cpp`を確認。
AsyncTCPの設定値は使用中の3.3.2のソースに基づく。ログの `cpu` は計測開始時、`pri` は計測開始時の実効優先度（継承により基本値から変わり得る）。

共有関係:

```text
loop / StorageTask(PPG + WAL) / async_tcp / ArchiveTask / Weather
                         ↓ 無期限待ち
                 StorageManager recursive mutex
                         ↓
              SD I/O + FRAM checkpoint / metadata
                         ↓ FRAM時はさらに
                     共通I²C mutex ← DisplayTask / sensor drivers
```

確認した長時間保持候補:

- WAL flush: rotation・SD remount・全pendingのFRAM read → transaction → SD検証 → consumeを1回のlock内で行う。
- 一覧: 512件の上限は**採用ファイル数**。不採用ファイルを含む走査entry総数には上限がなく、許可外directoryにも入る。ページ分割前に全走査する。
- PPG: `scanRawFile`はRAW全体を読んで検証するまでlockを保持。復旧用のprefix copy・environment復旧にも複数I/Oをまとめた区間がある。
- Archive: loopTask内の週次候補走査、worker内の入力検査とZIP I/O。statusMutexはStorageとは別なので、Storage所有者だけでは全待機を説明できない。
- download: current CSVはAsyncTCP内で同期forceFlush。Wi-Fiフラグを一時解除・復元するだけで、別taskのflush完了を非同期に待つ構造ではない。
- 短いmetadata getterでも、上記と同じlockを無期限に待つ。`/api/status`や`/api/altitude`も除外できない。

以上はコード上の構造であり、今回の再起動原因としての実測確定ではない。
全経路の待機時間・hold時間、PPG時の影響、Archive statusMutexの影響はR02継続項目。

## M01 計測実装

追加: `include/core/io_probe_state.h`、`include/services/io_probe.h`、`src/services/io_probe.cpp`。

- 計測中12件・完了待ち8件の固定RAM。満杯なら診断だけを捨て、`lost_active` / `lost_done`へ計上する。保存データを捨てるカウンタではない。
- 計測対象taskはRAM更新のみ。計測コードからSD・FRAM・Storage mutex・Serialを呼ばない。
- 別の `IoProbeTask`（core 0、priority 1、stack 4096 bytes）が250 ms周期で確認。500 ms以上継続する処理は、完了前から同一IDにつき最大1秒1回通知。
- 一覧、状態API 5本、CSV行は完了時に記録。append/flush等は50 ms以上、Storage lock待ちは500 ms以上を完了記録する。
- `StorageManager::lock`の挙動は無期限待ちのまま。全既存呼出元の関数名とtask、再帰深度、最外取得からの保持時間を観測する。
- 5秒ごとのhealthに、完了したlockの最大保持時間、loop開始間隔の最大値、現在のloop停滞時間、診断欠落数、heap最低値、診断taskのstack残量を出す。
- 起動時に実行ファームのELF SHA-256を表示する。

### 2026-09-10 認証障害に見えた事象の追加観測

- 実機は診断ファームで稼働し、設定済みのWeb資格情報を使ったDigest認証で `/` と `/api/session` がともに `200` を返した（0.035秒、0.053秒）。未認証時は `qop="auth"` を含むDigest challenge付きの `401` を正常に返した。
- その直後の `/`、`/app.css`、`/app.js` は各8秒でtimeoutした。Web応答停止前にシリアルで確認したuptimeは約429秒、再接続後は約168秒であり、途中で再起動したことを確認した。再起動後はAPがOFFになる。
- したがって今回の利用者症状は資格情報の拒否ではなく、認証成功後のWebアクセスを契機とする応答停止・再起動・AP解除が「ログイン不能」に見えたもの。どの送信／callbackが停止したかは、Watchdog直前の連続シリアルを未回収のためまだ確定しない。
- 認証設定は `admin` とAP接続時と同じpasswordを参照し、`secrets.h`は2026-09-06から変更されていない。password本文は診断へ記録しない。
- 次のbuildからindex/CSS/JS/sessionも `web.asset.*` / `web.session` として、認証前entryからsend呼出しまで計測する。

同じ再起動条件を必要なく繰り返さないため、次回はシリアル取得を先に開始してから静的資産1要求だけを実行する。

### 出力の読み方

- `active id=... op=web.files stage=wait`: 一覧callbackがStorage待ち。
- `owner task=... site=... held_us=...`: その時点のStorage所有者。wait直後の取得遷移では所有者なしの場合もある。
- `stage=open / scan / close`: SD open、再帰走査、root close＋unlockのいずれか。
- `stage=snapshot`: 現行CSV／PPG／Archive保護情報の取得。ここでは再びStorageやArchive statusMutexを待つ可能性がある。
- `filter / sort / json / send`: SD走査後の段階。sendは `request->send()`呼出しと残りのcallback処理であり、ブラウザ受信完了を保証しない。
- `done`と同一IDの`time_us` / `counts`: 1操作の要約。段階を再訪した場合の時間は累積。`result=returned`は成功判定ではなく、通常returnを意味する。
- `sd.csv_row`: `inspect/read`（末尾確認）、`open/write/flush/close/reopen/verify`の所要時間。closeは複数closeの合計。`bytes`はCSV本文長（改行を含まない）、実SD転送量ではない。
- 一覧の`bytes`は応答本文生成時のwrite戻り値合計（HTTPヘッダやTCP再送は除外）。`entries`はopenできた子entry数、`dirs`は実際に走査へ入ったdirectory数、`files`は採用数。
- 一覧の初回lock待ちは`wait`、走査用lock保持の近似は`open + scan + close`。heapは段階境界の標本最小値 `heap_sample_min` と、起動以降の全体最低値 `heap_low` を区別する。

制約:

- RAM診断は再起動・電源断で失われる。シリアルをPC側で取得してから再現する。既存 `scd41_events.json` にこの診断は入らない。
- 診断taskがCPUやSerialの都合で動けない場合、500 msで必ず出る保証はない。出力がないことだけで原因を除外しない。
- 診断もRAM・CPU・Serialを使うため、追加によって再現頻度が変わる可能性がある。実機でstack余裕・ログ欠落・センサー継続性を確認する。
- SDは4 MHzのまま。WAL/CSV形式、CRC、read-back後consume、PPG保存契約、Watchdogは変更していない。

## 実機手順（次の作業）

1. 診断ファームを書き込み、115200 bpsで起動からのシリアルログを取得する。起動行 `IoProbe ... ELF=`を必ず残す。
2. まずWi-Fi OFF・PPG IDLEで30秒程度観察。heap/stack余裕とhealthを確認する。本番SDを抜かない。
3. APへ接続し、**他の端末・通常WebUIタブを閉じて**同時アクセスを避ける。
4. WebUIの通常URL末尾へ `?io_probe=status` を付けて開く。状態API 5本＋sessionだけ取得し、定期更新と自動時刻送信は止まる。更新を1回試し、ログ保存。
5. `?io_probe=files`へ切り替える。sessionと一覧のみを取得し、状態APIを呼ばない。一覧完了／停止を確認し、必要な場合だけ一覧更新またはF5を1回試す。再起動した条件の反復は不要。
6. 調査モードは変更系APIをブラウザ側で抑止する。通常URLへ戻すと従来動作に戻る。古い資産が残る場合はキャッシュを無効にして読み直す。
7. `active`、`owner`、`done`、`time_us`、`counts`、`health`、Watchdog前後を回収する。カード条件とPPG/Wi-Fi状態も記載する。

現在SDで原因段階が特定できなければ、予備SDで空／少数file条件を比較する。
75件backlogの再試験は実データの消費を伴うため、保存済みデータを確保した条件で行い、旧形式を本番FRAMへ再注入しない。

判定:

| 観測 | 次に調べる範囲 |
|---|---|
| 状態のみでもwait＋StorageTask ownerで停止 | 一覧固有ではなく共有排他。D01でmetadata snapshotも分離 |
| 一覧のみでscanのentry増分が停止／非常に遅い | SD走査・card条件・entry構成。D02のworker/cache/budgetを実測に合わせる |
| filter/sort/jsonで停止 | CPU時間・heap・生成量。一覧上限と応答境界を再検討 |
| send前後まで戻ってもWDT | AsyncTCP応答経路・queueを追加計測。SD走査原因と断定しない |
| lost_*が増える／IoProbeTask stack不足 | 診断の観測能力を先に調整。欠けたデータでR01完了としない |
